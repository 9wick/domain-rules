# 設計思想・スコープ・背景

## なぜ作るのか

データの永続化前ロジックを手続き的に実装すると、次の問題が起きやすくなります。

- **ルール適用の条件が `if` 文に埋もれる**: 「新規作成のときだけ」「下書きから公開に変わるときだけ」といった条件がユースケースコードの中に散在し、仕様の全体像が追いにくくなります。
- **データ取得の重複と順序管理が手作業になる**: どのルールがどの参照データを必要とするかを意識しながら、取得処理の順番やキャッシュを毎回書くことになります。
- **既存値とのマージを毎回書く**: 更新処理のたびに「入力がなければ既存値を使う」というマージ処理をフィールドごとに書く必要が生じます。
- **ドメインルールがリポジトリに直接依存する**: ルール内で直接 DB やリポジトリを呼ぶと、単体テストにモックが必要になります。
- **「検証済み」が型で保証されない**: バリデーションを通さずに永続化オブジェクトを組み立てても、コンパイル時に防げません。

## 基本構造と責務の分離

### 1 本の直列パイプライン

1 回のメソッド呼び出しは、並べたステップを先頭から順に通る 1 本のパイプラインです。ライブラリがルールの実行順序を自動的に並び替えることはありません。前のルールで確定・昇格した型を後続のルールや永続化層が前提にできるようにするためです。

### モデル／アクションごとに 1 つのルールセット

保存に関するルールは「新規作成」「更新」「公開」など操作別ではなく、モデルごとに 1 つだけ定義します（「公開」は `status` が `DRAFT` から `PUBLISHED` に変わる保存として `when` で表現します）。これにより、どの画面・API から呼び出しても同じ不変条件が守られます。

### 部品と責務

| 部品          | 責務                                            | 主な要素                                             |
| ------------- | ----------------------------------------------- | ---------------------------------------------------- |
| `model`       | データの入出力の型定義                          | 入力スキーマ (`input`)、永続化スキーマ (`persisted`) |
| `action`      | 永続化を伴わない操作の入力型定義                | 入力スキーマ (`input`)                               |
| `port`        | 外部機能（副作用）の型宣言                      | 名前、引数・成功値・失敗値の型                       |
| `cached`      | 1 回の実行内でのポート結果のキャッシュ          | 元の `port`                                          |
| `rule`        | パイプラインの 1 ステップ                       | 名前、`requires`、`when`、`check`                    |
| `ruleset`     | ルールを順序通りに並べたパイプライン            | ルール列                                             |
| `modelRules`  | モデルに対するルール定義一式                    | `load` ポート、保存用 `ruleset`、削除用 `ruleset`    |
| `actionRules` | アクションに対するルール定義一式                | 判定用 `ruleset`、`output` 関数                      |
| `provide`     | ポートへの実装の割り当て                        | 実装関数または固定値 (`provide.value`)               |
| `bind`        | ルール定義とプロバイダーを結合し実行 API を生成 | —                                                    |

### アプリケーション内の配置

| レイヤー      | 配置場所                             | 役割                                                                                   |
| ------------- | ------------------------------------ | -------------------------------------------------------------------------------------- |
| ドメイン定義  | ドメインパッケージ                   | `model` / `action` / `port` / `rule` / `modelRules` / `actionRules` を定義して公開する |
| 依存解決 (DI) | アプリケーションのエントリーポイント | `bind` にルール定義一覧と `providers`（DB リポジトリや時計の実装）を渡す               |
| 実行          | ユースケース層                       | `bind` が返したメソッドを呼び出し、得られた `Persistable` 等をリポジトリへ渡す         |

この分離により、ドメインパッケージは DB やフレームワークの詳細に一切依存せずに済みます。

## 設計原則

- **直列パイプライン**: すべてのステップが `Result` を返し、最初の失敗で停止する。実行順は定義者が明示した順に従う。
- **対象と 1 対 1 のルールセット**: 操作ごとにルールセットを分けず、`when` によって値の変化から適用ルールを切り替える。
- **小さな独立単位**: `model`、`action`、`port`、`rule` はそれぞれ独立した値として定義し、後から組み合わせる。
- **型の昇格は状態の絞り込みのみで表現する**: 検証を通過したルールが値を返すことで状態型を狭める（アサーションだけの機能は持たない）。
- **境界で検証し、内部は信頼する**: 外部入力は最初の `input` ステップで検証する。`load` や `port` が返す既存値・取得値は信頼し、再検証しない。
- **副作用は `port` 経由で注入する**: 外部参照も時計 (`clock`) もすべて `port` として宣言し、`bind` で注入する。
- **単一フィールドの制約はスキーマ、相関制約はルール**: 更新時は入力にあるフィールドだけを検証するため、クロスフィールド制約はルールに書く。
- **マージ規則の単純化**: `undefined` は「変更しない」、`null` は「`null` で上書きする」。
- **同期的な `when`**: `when` はその時点の状態だけを見て同期的に判定する。
- **エラーの意味付けは利用者に委ねる**: ライブラリは失敗したステップ名 (`step`) だけを付与し、エラー値自体は利用者が定義する。
- **偽造できない証明**: 返り値（`Persistable` / `Deletable` / `Decision`）は private field で中身を保持し、別オブジェクトからの複製や別操作への流用を防ぐ。
- **状態遷移・認証・認可の専用機能は持たない**: これらも通常の述語関数やルールとして表現する。

## スコープ外

以下は本ライブラリの対象範囲外であり、アプリケーション側または基盤側で扱う想定です。

- **永続化処理そのもの**: `Persistable` や `Deletable` を受け取って実際に DB へ保存・削除するのはリポジトリの責務です。
- **並行実行時の整合性（TOCTOU）**: 一意性制約などは DB のユニーク制約やトランザクションと併用してください。
- **複数エンティティにまたがる一括更新**: 1 回のメソッド呼び出しで扱う対象は 1 つのモデル／アクションです。
- **API エンドポイント固有の入力制限**: 「この API では `status` しか受け付けない」といった制限は、ユースケース層の入力型で制限します。
- **HTTP / GraphQL 等からのデータ変換**: リクエストのデコードや引数への詰め替えはプレゼンテーション／ユースケース層の責務です。
- **時間経過による自動遷移や非同期ワークフローのオーケストレーション**。

## 先行事例・影響を受けた概念

- **Railway Oriented Programming** (Scott Wlaschin): `Result` を返す処理を直列につなぎ、失敗時にショートサーキットする実行モデルの基盤。
- **Haxl** (Facebook, _"There is no Fork"_, ICFP 2014): 同一実行内でのデータ取得の自動重複排除（`cached` ポートに相当。Haxl のような自動並列化・バッチ化は現状行わない）。
- **Ports and Adapters / Effect `Context.Tag`**: 必要な外部能力を型付きタグとして宣言し、実装を外から注入する設計。
- **Event-B / Design by Contract**: 不変条件と操作のガード条件を分離して記述する考え方。
- **Parse, don't validate** (Alexis King): 検証を通過したデータをより強い型へ変換し、未検証データの混入をコンパイル時に防ぐアプローチ。
- **Standard Schema**: スキーマライブラリ非依存の共通検証インターフェース。

## 未決定の論点

- **パイプライン長に対する型推論のパフォーマンス**: `add` を重ねるたびに状態の交差型（および条件付き昇格のユニオン型）が深くなります。15 ルール程度では問題ありませんが、大規模なルール数でのコンパイル速度は未計測です。
- **`cached` の引数比較**: 現在は `JSON.stringify` でキャッシュキーを生成しています。JSON シリアライズできない値の扱いや、`undefined` と `null` が同一キーとみなされる点は未整理です。
- **クライアント指定 ID での新規作成 (`upsert`)**: 現状の `upsert` は、指定 ID のレコードが存在しない場合に新規作成するのではなく `load` で `"NOT_FOUND"` 失敗とします。
- **ネストしたオブジェクトのマージと比較**: 現在の `merge` と `changed` / `immutable` はトップレベル（1 段目）のフィールドのみを対象としています。
- **`provider` / `clock` が例外を throw した場合の扱い**: 現在は `Result` を返さず例外を投げると返り値の Promise が reject されます。これを失敗型に組み込むかは未決定です。
- **`actor` 型の登録単位**: 現在は module augmentation (`Register`) によりアプリケーション全体で単一の `actor` 型を共有する設計です。
